# Лабораторная работа № 1. Нормализация данных в БД

6. Сравнить количество записей и общую стоимость продаж до и после нормализации.

## 2. Анализ нормализации и аномалий

### Функциональные зависимости

Для предметной области можно выделить следующие зависимости:

- `report_id → report_date, customer_id` — номер отчёта определяет дату и покупателя;
- `customer_id → customer_name` — код покупателя определяет его название;
- `product_id → product_name, price` — код товара определяет название и цену;
- `(report_id, product_id) → quantity` — в рамках отчёта для товара хранится его количество.

Естественный составной ключ исходной таблицы — `(report_id, product_id)`, поскольку один отчёт может содержать несколько товаров, а один и тот же товар может встречаться в разных отчётах.

### Первая нормальная форма (1NF)

Значения полей должны быть атомарными, а каждая строка должна описывать одну товарную позицию. В табличном представлении это правило соблюдается: товары одного отчёта представлены отдельными строками. Повторяющиеся сведения о покупателе и отчёте, однако, приводят к избыточности.

### Вторая нормальная форма (2NF)

Таблица должна находиться в 1NF, а каждый неключевой атрибут должен полностью зависеть от всего составного ключа.

В исходной структуре есть частичные зависимости:

- `report_date` и `customer_id` зависят только от `report_id`;
- `product_name` и `price` зависят только от `product_id`;
- `quantity` зависит от пары `(report_id, product_id)`.

Следовательно, исходная таблица не соответствует 2NF.

### Третья нормальная форма (3NF)

Таблица должна находиться в 2NF и не содержать транзитивных зависимостей неключевых атрибутов от ключа. Например, название покупателя определяется через код покупателя, а название и цена товара — через код товара. Эти сведения следует вынести в отдельные справочники.

### Аномалии исходной структуры

**Аномалия обновления.** Если название покупателя изменится, придётся изменить его во всех строках исходной таблицы. Если обновить не все строки, в базе появятся противоречивые сведения.

Для демонстрации (изменение отменяется после проверки):

```sql
START TRANSACTION;

UPDATE sales_unnormalized_2
SET customer_name = 'Новое название'
WHERE customer_id = 12
LIMIT 1;

SELECT customer_id, customer_name
FROM sales_unnormalized_2
WHERE customer_id = 12;

ROLLBACK;
```

**Аномалия удаления.** Если удалить единственную строку отчёта покупателя 23, одновременно исчезнет единственная запись, содержащая сведения об этом покупателе.

```sql
START TRANSACTION;

DELETE FROM sales_unnormalized_2
WHERE report_id = 1102;

SELECT DISTINCT customer_id, customer_name
FROM sales_unnormalized_2
WHERE customer_id = 23;

ROLLBACK;
```

**Аномалия вставки.** В исходной таблице нельзя полноценно хранить покупателя или товар отдельно от отчёта и товарной позиции. Попытка добавить строку только с данными покупателя потребует оставлять остальные поля пустыми либо вносить фиктивные значения.

```sql
INSERT INTO sales_unnormalized_2
    (customer_id, customer_name)
VALUES
    (99, 'Новый покупатель');

-- Удаляем демонстрационную строку, чтобы не менять исходный набор данных.
DELETE FROM sales_unnormalized_2
WHERE customer_id = 99;
```

Последний пример показывает, что структура допускает неполную строку, но не предоставляет отдельного места для хранения покупателя как самостоятельной сущности.

## 3. Проектирование схемы в 3NF

Для устранения избыточности исходная таблица разделяется на четыре таблицы.

| Таблица | Назначение | Ключи |
|---|---|---|
| `customers` | Справочник покупателей | `customer_id` — PK |
| `products` | Справочник товаров | `product_id` — PK |
| `reports` | Дата и покупатель отчёта | `report_id` — PK, `customer_id` — FK |
| `report_items` | Товарные позиции отчёта | составной PK `(report_id, product_id)`, оба поля — FK |

Связи между таблицами:

- один покупатель может иметь несколько отчётов;
- один отчёт принадлежит одному покупателю;
- один отчёт содержит несколько товарных позиций;
- один товар может входить в разные отчёты.

### Создание таблиц

```sql
CREATE TABLE customers (
    customer_id   INT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

CREATE TABLE products (
    product_id   INT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    price        DECIMAL(10,2) NOT NULL
);

CREATE TABLE reports (
    report_id   INT PRIMARY KEY,
    report_date DATE NOT NULL,
    customer_id INT NOT NULL,
    CONSTRAINT fk_reports_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);

CREATE TABLE report_items (
    report_id  INT NOT NULL,
    product_id INT NOT NULL,
    quantity   INT NOT NULL,
    PRIMARY KEY (report_id, product_id),
    CONSTRAINT fk_items_report
        FOREIGN KEY (report_id)
        REFERENCES reports(report_id),
    CONSTRAINT fk_items_product
        FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);
```

В новой структуре справочные сведения хранятся по одному разу. Внешние ключи обеспечивают ссылочную целостность, а составной первичный ключ не позволяет дважды добавить один и тот же товар в один отчёт.

## 4. Перенос данных

Сначала перенесём уникальных покупателей, товары и отчёты, затем — позиции отчётов.

```sql
INSERT INTO customers (customer_id, customer_name)
SELECT DISTINCT customer_id, customer_name
FROM sales_unnormalized_2;

INSERT INTO products (product_id, product_name, price)
SELECT DISTINCT product_id, product_name, price
FROM sales_unnormalized_2;

INSERT INTO reports (report_id, report_date, customer_id)
SELECT DISTINCT report_id, report_date, customer_id
FROM sales_unnormalized_2;

INSERT INTO report_items (report_id, product_id, quantity)
SELECT report_id, product_id, quantity
FROM sales_unnormalized_2;
```

Порядок важен: сначала добавляются записи родительских таблиц, на которые ссылаются внешние ключи, и только после этого — строки таблицы `report_items`.

## 5. Проверка переноса

### Количество записей

```sql
SELECT 'source_rows' AS table_name, COUNT(*) AS row_count
FROM sales_unnormalized_2
UNION ALL
SELECT 'customers', COUNT(*) FROM customers
UNION ALL
SELECT 'products', COUNT(*) FROM products
UNION ALL
SELECT 'reports', COUNT(*) FROM reports
UNION ALL
SELECT 'report_items', COUNT(*) FROM report_items;
```

Для исходного набора ожидается:

- исходная таблица — 7 строк;
- `customers` — 3 покупателя;
- `products` — 4 товара;
- `reports` — 5 отчётов;
- `report_items` — 7 позиций.

### Сравнение общей суммы

До нормализации:

```sql
SELECT SUM(price * quantity) AS total_before
FROM sales_unnormalized_2;
```

После нормализации:

```sql
SELECT SUM(p.price * ri.quantity) AS total_after
FROM report_items AS ri
JOIN products AS p ON p.product_id = ri.product_id;
```

Для исходных данных ожидаемая сумма — **3 609 000.00**. Значения `total_before` и `total_after` должны совпасть.

### Проверка содержимого новой схемы

```sql
SELECT
    r.report_id,
    r.report_date,
    c.customer_id,
    c.customer_name,
    p.product_id,
    p.product_name,
    p.price,
    ri.quantity
FROM report_items AS ri
JOIN reports AS r
    ON r.report_id = ri.report_id
JOIN customers AS c
    ON c.customer_id = r.customer_id
JOIN products AS p
    ON p.product_id = ri.product_id
ORDER BY r.report_id, p.product_id;
```

### Пример аналитического запроса

Узнаем общую стоимость товарных позиций в отчётах покупателя с кодом 12:

```sql
SELECT
    c.customer_id,
    c.customer_name,
    SUM(p.price * ri.quantity) AS total_spent
FROM customers AS c
JOIN reports AS r
    ON r.customer_id = c.customer_id
JOIN report_items AS ri
    ON ri.report_id = r.report_id
JOIN products AS p
    ON p.product_id = ri.product_id
WHERE c.customer_id = 12
GROUP BY c.customer_id, c.customer_name;
```

Для предоставленного набора данных ожидаемый результат — **2 925 000.00**.

Исходную таблицу следует удалять только после того, как все проверки выполнены и сохранён резервный дамп. В рамках лабораторной работы её можно оставить для сравнения.

## 6. Резервное копирование и журналирование

До нормализации необходимо сохранить дамп исходной базы, а после переноса — дамп базы с нормализованной схемой. Команды запускаются в терминале хост-системы; вместо `<container_name>` и `<mysql_user>` указываются фактические имя контейнера и пользователь MySQL.

Пример экспорта:

```bash
docker exec <container_name> mysqldump -u<mysql_user> -p normalization_task > dumps/normalization_task.sql
```

Если создаются отдельные дампы до и после нормализации, имена файлов должны однозначно отражать этап, например:

- `dumps/before_normalization.sql`;
- `dumps/after_normalization.sql`.

Пароль при запросе вводится в терминале, не следует сохранять его в README или в Git.

Лог должен содержать только фактически выполненные действия пользователя: команды, запросы и последовательность шагов. Не добавляйте в лог вымышленные записи или результаты. Скриншоты должны подтверждать реальные результаты выполнения запросов и этапов работы.

## 8. Вывод

В ходе лабораторной работы рассматривается переход от одной таблицы с повторяющимися сведениями к набору связанных таблиц, соответствующих третьей нормальной форме. Разделение данных на справочники покупателей и товаров, заголовки отчётов и товарные позиции уменьшает избыточность и позволяет избежать аномалий обновления, вставки и удаления.

Корректность нормализации подтверждается сохранением количества товарных позиций, совпадением общей суммы до и после переноса, а также успешным выполнением запросов через связи между таблицами. Фактические результаты, дампы, журнал и скриншоты добавляются исполнителем после выполнения команд.
